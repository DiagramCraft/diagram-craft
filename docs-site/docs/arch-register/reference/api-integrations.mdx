# API And Integrations

Arch Register's HTTP API is defined as oRPC contracts and exported as an OpenAPI 3.1 specification. The full,
generated endpoint-by-endpoint reference is published as a static [API Reference](pathname:///arch-register/api.html)
page, rendered with [Redoc](https://github.com/Redocly/redoc) and grouped by domain via the spec's operation tags
(Enums, Schemas, Entities, Projects, and so on). This page covers where that reference comes from and how to keep
it up to date.

## API surfaces

New consumers should choose the surface that matches their role:

- `/api/application/v1/*` is the first-party application surface. It is being introduced domain by domain while
  existing `/api/*` routes remain available for compatibility.
- `/api/integrations/v1/*` is the versioned REST surface for supported third-party integrations. It includes entity
  and typed-relation operations, external-identity synchronization, API specification synchronization, sync-run
  tracking, and external governance operations.
- `/api/adapters/diagram-craft/*` is the Diagram Craft-specific adapter surface. The existing `/api/public/*` paths are
  authenticated compatibility aliases; `public` is not a security boundary.
- `/mcp` is a separate MCP protocol endpoint, documented under [MCP Server](mcp-server), rather than a REST path.

The legacy `/api/*` surface remains available for compatibility. Clients can use a versioned surface when it provides
the operation they need; breaking changes to a versioned surface require a new major URL version.

## Tokens and permissions

Users can create personal API tokens from [Account Settings](../use/account-settings). Workspace administrators can
also create workspace-scoped tokens backed by a system user from [Workspace Settings](../admin/workspace-settings).
Both token types are limited to the capabilities selected for them; copy the secret when it is created and revoke it
when it is no longer needed.

Choose capabilities for the operations the integration calls. Entity data reads require `content.view`; workspace and
schema discovery may also require `ws.view`. Ordinary entity or relation mutations require `ent.edit`. Integrations
that update only fields marked as externally managed can use `ent.external_update`. API specification operations may
also require `artifact.manage`, and viewing raw specification content requires `artifact.content.view`. Endpoint
authorization and field-group access checks still apply to every request.

## Current route inventory

The table summarizes the currently served surfaces. Consult the generated API Reference for the operation-level
request, response, and error contracts.

| Surface | Current routes | Purpose |
| --- | --- | --- |
| Legacy application API | `/api/workspaces`, `/api/:workspace/*` | Existing application operations, including catalog, projects, configuration, governance, jobs, documents, and webhooks |
| Application v1 | `/api/application/v1/:workspace/*` | Versioned first-party application contracts, including catalog and AI operations |
| Integration v1 | `/api/integrations/v1/:workspace/*` | Supported third-party contracts, including entity/relation sync, API specifications, sync tracking, and external governance |
| Diagram Craft adapter | `/api/adapters/diagram-craft/:workspace/*` | Authenticated adapter operations for Diagram Craft |
| Legacy adapter alias | `/api/public/:workspace/*` | Compatibility paths for the authenticated Diagram Craft adapter; these routes are not anonymous |
| Authentication | `/api/auth/*` | Browser sign-in and session flows |
| Development | `/api/dev/*` | Environment-gated development endpoints; not a supported integration surface |
| MCP | `/mcp`, with legacy `/sse` and `/messages` transports | Standalone MCP protocol server; see [MCP Server](mcp-server) |
| OpenAPI descriptions | `/openapi.yaml`, `/openapi.json`, and surface-specific `/openapi/*.json` | Generated descriptions of the live contracts |

Surface ownership is not exclusive: a contract may be exposed on both application and integration surfaces when the
behavior, authorization, and representation are the same.

## Compatibility policy

- Existing `/api/*` routes are the compatibility baseline. A migration adds a new route alias or canonical route before
  changing any existing consumer.
- A domain may be aliased on both `/api/application/v1/*` and `/api/integrations/v1/*` when both consumers need the same
  contract. Choose one primary owner for documentation and lifecycle decisions, and record the second path as an
  intentional alias rather than maintaining separate business logic.
- An alias must call the same contract handler and authorization path as its canonical route. It must not duplicate
  business logic or weaken authentication.
- Aliases preserve HTTP methods, request and response shapes, error behavior, and path parameters. The only permitted
  transformation is the URL prefix mapping documented for that surface.
- New public contracts use `/v{major}` in the surface path. Additive changes are allowed within a major version;
  breaking changes require a new major version and a migration note.
- `/api/public/*` is a naming-compatibility path, not an anonymous API. Authentication and workspace permissions apply
  exactly as they do to the adapter route.

## Deprecation and removal

When a replacement is live, update consumers and docs first, then mark the old path as compatibility-only. Removal of a
legacy path requires all of the following:

1. the replacement has a published contract and OpenAPI description;
2. first-party consumers have used the replacement for one release cycle;
3. external consumers have a migration note and a warning period;
4. request metrics show no material usage of the old path, or remaining consumers have an agreed migration owner; and
5. the removal is called out in release notes and covered by a regression test proving the replacement remains live.

Until those criteria are met, compatibility aliases remain supported and are not silently redirected, since redirects can
change methods, authentication handling, or streaming behavior.

## Primary Sources

- server OpenAPI specification, generated to `arch-register-packages/server/openapi.json`
- oRPC contract definitions in `arch-register-packages/api-types`
- unified spec assembly in `arch-register-packages/server/src/openapi.ts`
- application surface specification at `/openapi/application-v1.json`
- integration surface specification at `/openapi/integrations-v1.json`
- Diagram Craft adapter specification at `/openapi/adapters/diagram-craft.json`

## Updating The API Reference

The [API Reference](pathname:///arch-register/api.html) page is a static HTML file built from the committed
`openapi.json` file, not derived live from source. After changing an oRPC contract in
`arch-register-packages/api-types`:

1. Regenerate the spec and commit the result:
   ```bash
   pnpm --filter @arch-register/server openapi:generate
   ```
2. That's it — the docs site rebuilds the static API reference page from the committed spec as part of
   `pnpm docs:dev` and `pnpm docs:build` (a fast standalone bundling step, not a slow regeneration process, so it
   doesn't meaningfully affect dev server startup time). A CI check
   (`pnpm --filter @arch-register/server openapi:check`) fails the build if `openapi.json` is out of sync with the
   contracts, so a forgotten regeneration step won't silently go stale.

## Other Integration Surfaces

Besides the HTTP API:

- the [MCP Server](mcp-server) exposes entity and typed-relation discovery, traversal, and mutation tools for AI and automation clients
- [Integration Sync](integration-sync) covers entity, relation, and API specification synchronization, including the
  Backstage example
- [Webhooks](../admin/webhooks) deliver signed workspace events to external systems
- [Scheduled Jobs](../admin/scheduled-jobs) and [Automation Rules](../admin/automation-rules) cover recurring and
  event-driven workspace work
- the [External Integration Example](external-integrations) demonstrates a complete webhook-to-API
  write-back service
- [External Content](../use/content#experimental-external-content) describes the experimental Git repository mount
  workflow

External governance workflows are available through the integration API and are currently **experimental**. See
[External Governance](external-integrations#experimental-external-governance-workflows) for the capability and setup
overview.
