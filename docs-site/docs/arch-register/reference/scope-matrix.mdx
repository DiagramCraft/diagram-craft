# Scope Matrix

This page is a quick reference for where content lives and which access rules apply to it.

| Scope | Best for | Parent boundary | Content access is primarily controlled by | Typical content |
| --- | --- | --- | --- | --- |
| Workspace | Shared docs and diagrams | Workspace | Workspace role capabilities: `content.view` and `content.edit` | Standards, shared notes, common diagrams |
| Entity | Record-specific context | Entity | Workspace role capabilities: `content.view` and `content.edit`; entity data and fields have their own access rules | Attached docs, diagrams, files, runbooks |
| Project | Initiative-specific material | Project and owner team | Project and owner-team authorization | Project wiki pages, diagrams, uploads |
| Application | Optional domain workflows | Workspace | Application access policy | Glossary, strategy, and other enabled apps |

## Rule Of Thumb

- Use workspace content for material shared across the workspace.
- Use project content for an initiative; workspace `content.view` and `content.edit` do not grant project content access.
- Use entity content for context attached to one record; access to its content is separate from access to restricted entity fields.
- Team ownership controls applicable entity and project actions. It does not replace workspace membership or the content permissions listed above.
- Restricted field groups hide or limit individual entity fields even when the record or its content is visible.
