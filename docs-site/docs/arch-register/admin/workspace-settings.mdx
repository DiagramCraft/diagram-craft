# Workspace Settings

Workspace Settings is the main governance screen for a workspace.

The settings sidebar shows sections allowed by your permissions. A global platform administrator or a member with the
workspace capability required by that section can manage it; requirements differ for model, people, and operational
settings. Ask a workspace administrator if a section is missing.

## Covered Areas

The implemented settings area includes:

- general workspace identity
- application capability bindings and application access policies
- supported currencies, default currency, and assessment types
- lifecycle
- model overview
- entity types (schemas)
- document types and templates
- roles and permissions
- application access
- global permissions
- teams
- members
- AI
- workflows
- export and import
- analytics
- audit log
- API tokens
- webhooks
- job monitoring
- danger zone

## General

Use **Workspace Settings → General** to manage the basic workspace identity such as name, slug, description, visual
identity, and workspace date/time display preferences. Date choices include ISO, month-name, and day/month formats;
time can use a 12-hour or 24-hour clock. The preference applies across entity drawers, fields, tables, dashboards,
assessments, and governance views. Date-only values stay on the same calendar day regardless of the viewer's timezone.
New workspaces use ISO dates and 24-hour time by default.

## Currencies And Assessment Types

Open **Workspace Settings → Currencies** to choose the supported currencies and the workspace's default currency.
Open **Workspace Settings → Assessment types** to manage the categories used to organize workspace assessments and
their dashboard views.

## Lifecycle

Open **Workspace Settings → Lifecycle** to define the states available for entities and choose the deprecated state.
Lifecycle classifies maturity and supports filtering; it does not grant or deny access.

One state can be designated as the workspace's deprecated state. Finalizing an
[entity deprecation](../use/governance) moves the entity to that state.

## Applications And Capabilities

Open **Workspace Settings → Applications & Capabilities** to enable an optional application and connect its required
roles to workspace schemas. Use the Access tab to choose all members or selected people and teams. The capability
binding determines whether the app is configured; the access policy determines who may open it. See
[Workspace Templates and Capabilities](workspace-templates-capabilities) for the setup sequence and
[Roles and Permissions](roles-permissions) for the access rules.

## Governance Policies

Use **Workflows** to configure governance behavior centrally. Each saved workflow configuration can define the
approval strategy and quorum, reminder schedule, escalation strategy, fallback users and teams, and case-kind-specific
extensions. Configurations may be workspace-wide or scoped to a supported case subkind, such as a document type and
status field. Workspace admins are the final fallback when no configured target resolves.

Entity change approval and entity deprecation are configured in **Workflows** rather than on the entity schema editor.
Administrators can set:

- **Entity approval policy** — require approval before entity changes take effect
- **Entity deprecation** — require a deprecation proposal to retire entities of this type

Document status approval is also configured in **Workflows**. Select the document type and enum field, then choose the
status values that require approval. Approval and escalation can independently use a user or team field from the
document type, with configured users or teams as fallbacks. The document schema editor continues to define fields and
values but does not contain workflow configuration.

See [Governance and Approvals](../use/governance) for how these workflows behave for users.

## Document Types And Templates

Document Types & Templates defines the structured Markdown documents available in the workspace. Document types
provide fields and validation rules; templates provide reusable Markdown bodies and metadata defaults. Project owners
can also create project-specific Markdown templates from project settings.

See [Document Types And Templates](document-types-templates) for the full configuration and usage workflow.

## Analytics And Audit

Open **Workspace Settings → Analytics** for catalog coverage, lifecycle distribution, ownership gaps, and completeness.
Open **Workspace Settings → Audit log** to inspect activity by object type and date range. They answer different
questions: analytics summarizes the catalog; audit records changes. Access requires the relevant workspace permission.
See [Analytics and Audit](analytics-and-audit) for what each screen shows and how restricted field values are handled.

## Administration

The **Administration** group collects settings for operating the workspace day to day, separate from its data model
and membership:

- **API tokens** creates workspace-scoped API tokens backed by a system user, each restricted to a chosen subset of
  role capabilities and with an optional expiry date, for use by external clients and integrations.
- **Webhooks** configures outbound webhooks for workspace events and shows delivery behavior, so external systems
  can react to changes in Arch Register.
- **Job monitoring** shows scheduled jobs, job servers, and run history, with cancellation available for supported
  jobs.
- **Danger zone** for irreversible operations.

## Application Access

Use **Applications** to control who can use each installed optional application. Application access is an
independent policy from workspace roles and can grant access to all workspace members or selected people and teams.
Team and individual grants are additive.

Access is deny-by-default for ordinary members until a policy is configured. Users must also have workspace view
access. Global administrators and workspace role managers always retain access. Removing a policy returns the
application to administrator-only access; Home is always available.

## Public Catalog

**Public catalog** configures the separate unauthenticated read-only catalog. Select only the schemas, fields, entities,
wiki pages, and API specifications that may be shared externally. See [Public Catalog](public-catalog) for its preview,
indexing, and reader behavior.
