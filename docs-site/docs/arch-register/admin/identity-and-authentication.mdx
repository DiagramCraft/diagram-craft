# Identity And Authentication

Arch Register sign-in is configured for the deployment. Workspace administrators manage membership and workspace roles;
platform administrators manage local user accounts when local authentication is enabled.

## Sign In

Open the deployment's web app and use the method shown on its sign-in screen:

- **Local authentication** uses a username and password for an account in Arch Register.
- **OIDC single sign-on** redirects to the identity provider configured by the deployment. OIDC is experimental; a
  deployment administrator configures it in the server environment, not in Workspace Settings.

If you can sign in but cannot enter a workspace, ask a workspace administrator to add you under **Workspace Settings →
Members** and assign the appropriate workspace role. An account and workspace membership are separate: creating an
account does not by itself grant access to every workspace.

## Manage Local User Accounts

In local-authentication deployments, platform administrators with the global `admin_platform` permission can create and
update local user accounts, deactivate or reactivate them, and change their passwords. User management is available
from the workspace **Members** settings when local authentication is enabled. It is unavailable when OIDC is enabled;
the identity provider manages sign-in credentials in that mode.

Workspace administrators can manage membership and workspace roles separately. See [Teams and Members](teams-members)
and [Roles and Permissions](roles-permissions).

## Login Protection

Local sign-in is protected against password guessing:

- **Account lockout.** After 5 consecutive failed attempts for a username the account is locked for 1 minute. Each
  further failure doubles the lock, up to 1 hour. A successful sign-in resets the counter, and failures older than
  15 minutes stop counting.
- **Per-IP limit.** A client IP that makes 20 failed attempts within 5 minutes is blocked for the rest of that window.
- **Same response for every username.** Unknown usernames are throttled exactly like real ones, so the limits do not
  reveal which accounts exist. Locked or blocked requests receive HTTP 429 with a `Retry-After` header, and a correct
  password is also rejected while an account is locked.

Platform administrators can end a lockout early from **Global Settings → Users** by choosing **Unlock sign-in** on a
locked user. **Global Settings → Security events** lists sign-ins, failed attempts, rate limiting, lockouts and unlocks
with the username and client IP. Events are kept for 90 days.

Limits are stored in the database, so they apply across multiple server instances. When the server runs behind a
reverse proxy or load balancer, set `TRUST_PROXY` to the number of proxies in front of it so the real client IP is used;
otherwise every client appears to come from the proxy. Leave it unset when the server is exposed directly, because
forwarded headers can then be spoofed.

| Environment variable | Default | Purpose |
| --- | --- | --- |
| `LOGIN_MAX_FAILURES` | `5` | Consecutive failures before an account is locked |
| `LOGIN_LOCKOUT_BASE_SECONDS` | `60` | First lock duration, doubled for each further failure |
| `LOGIN_LOCKOUT_MAX_SECONDS` | `3600` | Maximum lock duration |
| `LOGIN_FAILURE_WINDOW_SECONDS` | `900` | Failures older than this stop counting |
| `LOGIN_IP_MAX_ATTEMPTS` | `20` | Failed attempts per client IP within the IP window |
| `LOGIN_IP_WINDOW_SECONDS` | `300` | Length of the per-IP window |
| `AUTH_EVENT_RETENTION_DAYS` | `90` | Retention for security events |
| `TRUST_PROXY` | `0` | Number of trusted reverse proxies |

## Development-Only User Switcher

The optional user-switcher toolbar is an experimental development tool. It bypasses normal sign-in and lets a developer
assume an account from the local database. It is available only when the server runs in development mode and
`DEV_USER_SWITCHER_ENABLED=true`; production mode disables it regardless of that flag. Do not enable it on a deployed
production instance.
