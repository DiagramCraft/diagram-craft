# Governance And Approvals

Workspace administrators configure review workflows in **Workspace Settings → Workflows**. A workflow can route
changes to approvers, request acknowledgements, and configure deadlines, reminders, and escalation where supported.
This guide explains where to find tasks and how the supported entity and document workflows behave.

## Find And Review Work In My Work

Open **My Work** from the navigation rail to review governance tasks:

- **Assigned** lists open tasks waiting on you. Filter by state, task kind (approve, acknowledge, review, or remediate),
  case kind, and due date (overdue or due within a week).
- **Completed** shows your completed task history.
- **Submitted** lists work you started and shows what or who is blocking it. Where the workflow allows it, withdraw an
  open submission from this view.

Select a task to open its governed record and available action. The actions depend on the workflow: an approver may
approve or request changes, a deprecation approver may also reject, and an affected team may need to acknowledge.
When an open case has outstanding assignees, its initiator can send them an on-demand reminder from Submitted. These
reminders are rate-limited. Governance action items also appear in the [notification feed](collaboration-notifications)
and clear automatically when the task is resolved, superseded, or cancelled.

## Configure Reminders And Escalation

For cases with deadlines, scheduled reminders notify still-open assignees as a deadline approaches and again after it
passes. The supported reminder workflows include entity change proposals, entity deprecations, relation change
proposals, document status approvals, and assessment responses. Each workflow can use its own approaching and overdue
cadence; reminders respect each recipient's notification preferences and are not repeated after that reminder window
has fired for a case. My Work highlights overdue tasks. See [Assessments](assessments) for assessment response tasks.

Workspace administrators configure reminder schedules in **Workspace Settings → Workflows**. A configuration can
enable or disable reminders and set a cadence for a workflow or supported case subtype.

Escalation is available for entity change proposals, entity deprecations, and document status approvals. If an open
case remains unresolved past its configured overdue threshold, it is escalated once. The workflow's escalation
strategy resolves recipients first, followed by configured fallback users or teams; workspace administrators are the
final fallback. The escalation is recorded in the case activity and shown with a badge in My Work. Administrators can
enable or disable escalation and set its strategy, threshold, and fallback targets alongside reminders. Relation
change proposals and assessment responses support reminders but do not support escalation.

Administrators can also configure ordered, typed initiation fields for supported workflows. When starting a case, the
initiator supplies required values; those values remain visible on the case, in the inbox and related notifications,
and in applicable escalation and integration messages.

## Approve Entity Changes

Administrators can require approval for entity changes, optionally scoped to a schema. To submit a proposal, a user
needs view and edit access to the entity and the workspace `ent.propose` capability. Saving a proposed change creates
an immutable revision; the live entity is unchanged until approval. Approvers review a before-and-after diff and can
approve or request changes; a reason is required when requesting changes. The proposed state is applied once the
configured quorum of distinct approvers has approved it. If changes are requested, the submitter can revise and
resubmit a single-entity proposal.

Bulk-edit-originated proposals bundle changes to several entities into one governance case; they do not have the
single-entity resubmit path. Approval targets use the configured entity-owner-admin strategy, then fallback users or
teams, with workspace administrators as the final fallback. If you are the sole eligible approver, you may
self-approve. Authorized users can bypass approval with a reason; the bypass is recorded in the audit trail. Restricted
field-group values remain hidden from reviewers who cannot view those fields. A user with the workspace `ent.override`
capability can bypass approval with a reason; the bypass is recorded in the audit trail.

## Entity Deprecation

Administrators can enable a schema-scoped deprecation workflow. To propose a deprecation, a user needs view and edit
access to the entity and the `ent.propose` workspace capability. Enter the target date and reason, and optionally name
a successor entity and related project. Approvers can approve, reject, or request changes. Affected owner teams have
separate acknowledgement tasks. Approval targets use the entity-owner-admin strategy, configured fallbacks, and the
workspace-administrator final fallback.

While the proposal is in flight, an authorized user can postpone or cancel it. It can be finalized on schedule, which
moves the entity to the state designated in **Workspace Settings → Lifecycle**. Deprecation does not merge the entity
or rewrite its references; use [Merge Entities](entity-merging) to consolidate a duplicate record.

## Approve A Document Status

Administrators configure document status approval for an enum field on a document type and select which status values
require approval. Users with permission to edit the document can change its status; values not selected for approval
continue without a governance case. An approval task is assigned according to the workflow configuration. For
approval and escalation targets independently, administrators may select an active user or team field from the
document type. If that field has no valid value, configured fallback users and teams are used, followed by workspace
administrators. Approvers can approve or request changes. See
[Document Types And Templates](../admin/document-types-templates) for setting up typed documents.

## Merge A Duplicate Entity

Entity merging is a privileged, review-and-confirm action rather than a governance approval case. It requires the
`ent.merge` capability and entity administration access on both records. The wizard lets an authorized user preview
the impact, resolve editable conflicts, acknowledge supported warnings, and confirm the merge. An open governance case
on the source blocks the merge. Read the [Merge Entities guide](entity-merging) for the conflict, scope, and record
transfer details.
