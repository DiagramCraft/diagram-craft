# Governance And Approvals

Workspaces can require review before certain changes take effect. Administrators configure governance centrally in
**Workspace Settings → Workflows**, where each case kind can expose supported approval, reminder, escalation, and
case-specific settings. This page covers the governance inbox and the governed workflows users interact with.

## My Work

**My Work** in the navigation rail is the governance inbox. It shows an open-task count badge and has two scopes:

- **Assigned** lists open governance tasks waiting on you, with completed task history available separately
- **Submitted** lists governance work you have started, so you can see what — or who — is currently blocking it

Filter tasks by state, task kind (approve, acknowledge, review, remediate), case kind, and due date (overdue, or due
within a week). Each task links back to the governed record.

From the **Submitted** scope you can withdraw an open submission where permitted.

Governance tasks also appear as action items in the [notification feed](collaboration-notifications); those
notifications clear automatically when the underlying task is resolved, superseded, or cancelled.

## Entity Change Approval

Administrators can require approval for entity changes by adding an entity-change workflow configuration in
**Workspace Settings → Workflows**. The configuration can be scoped to a schema. When approval is required:

1. Saving a change submits an immutable revision instead of updating the entity directly.
2. Approvers review a before/after diff of the proposed change.
3. Approvers approve, or request changes — after requested changes, the submitter can resubmit.
4. On approval, the proposed state is applied to the live entity.

Two special cases are supported:

- if you are the sole eligible approver, you can self-approve your own submission
- authorized users can record an approval bypass, which is captured in the audit trail

Approval targets use the configured entity-owner-admin strategy, followed by configured fallback users or teams.
Workspace administrators are used if no approval target resolves. The configured approval quorum determines how many
distinct approval slots and actors are required.

## Entity Deprecation

Administrators can configure a schema-scoped entity deprecation workflow in **Workspace Settings → Workflows**. When
enabled, retiring an entity goes through a deprecation proposal rather than a direct lifecycle edit:

- propose a deprecation with a target date, a reason, an optional successor entity, and an optional related project
- the proposal routes through approval like other governed changes
- affected owner teams are notified and asked to acknowledge the deprecation
- the deprecation can be postponed, finalized on schedule, or cancelled while in flight

Deprecation approval uses the same entity-owner-admin strategy and fallback rules. Affected owner teams retain their
separate acknowledgement tasks.

Finalizing moves the entity to the workspace's designated deprecated lifecycle state, configured in
**Workspace Settings → Lifecycle**.

## Document Status Approval

Document status approval is configured for a document type's enum field in **Workspace Settings → Workflows**. The
workflow configuration uses the shared approval and reminder settings, while its document-status extension identifies
the status values that require approval. Status values that are not selected continue without an approval case.
Approval and escalation can independently use a selected active user or team field from the document type. If the
field has no valid value, configured fallback users and teams are used, followed by workspace administrators. Escalation
is available only for case kinds that register escalation support; assessment responses remain notification-only.
